The problem

Nobody is careless. The paper just moves faster than the record of it.

In a busy registry a single file can change hands five or six times in a week. Each handoff is real, but only some are written in a logbook. When a student, a parent, or the Vice-Chancellor's office asks where a file is, the search starts from memory.

🔍

The search

Finding one file means walking to offices, asking colleagues, and waiting. The work stops while the search happens.

⏳

The silent stall

A file waiting two days for a signature looks exactly like a file waiting three weeks. Nothing signals the difference.

🛡️

The hard question

"Which office has been holding this file since October?" Today there is no honest answer to give.

How it works

One scan or one typed number. That is the whole habit.

The file does not need to be digitised for us to know where it is. It only needs to be recorded when it changes hands — by the person receiving it, under their own name.

What it changes

Small system. Very specific promises.

For the Registrar

A defensible record. When a query comes from the Vice-Chancellor's office or from a graduate abroad, the trail exists — every office, every date, every signature. The office can account for itself.

For the Registry staff

No more blame for delays that happened elsewhere. The record shows the file arrived here on Monday and left on Tuesday, and where it went next.

For departments

A clear queue instead of a pile. Staff can see what is waiting on them and what they have already released.

For students and alumni

A real status instead of "come back next week." The number of trips to campus drops because the waiting becomes visible.

Honest scope

What FileTrail does not do

Being clear about limits is how a small system earns trust in an institution.

Not thisBecause
It does not replace paper filesThe physical file remains the record of authority. We record its movement, nothing more.
It does not scan or store documentsDigitising an archive is a separate, much larger project. It is not needed to know where a file is.
It does not approve anythingSignatures and approvals stay human and stay on paper. We only record that they happened.
It does not replace staff or judgementIt answers one question well: where is this file, and who has been holding it.
It does not expose individualsReports are by office, not by person. The system should make a clerk look organised, not hunted.
Proposed pilot

One flow. One department. Four weeks.

We are not proposing to change how the University works. We are proposing to measure one process properly, so that any decision afterwards is based on facts rather than impressions.

  1. Week 1 — Observe. Sit with the Registry and one department. Map the real journey of one file type, with counts: offices touched, days taken, where it stalls.
  2. Week 2 — Set up. Register the offices and staff who handle the chosen flow. No new hardware, no scanning, no rewiring.
  3. Weeks 3–4 — Run. Staff record movements as they already hand files over. A weekly summary goes to the Registrar's office.
  4. Afterwards — Review. A short written report: what the data showed, what changed, and whether it is worth continuing.

Why a student is proposing this

Because the person who carries the file between offices is in the best position to describe the journey honestly. As General Representative of the Department of Computer Science, this project began with a simple observation: the same file can be carried five times in a week, and still nobody can say where it is.

FileTrail is the record of those journeys — built here, for here, with the Registry's actual process as the specification rather than an assumption about it.
